### Top-Level Folders
---
#### At the root of the 'vueapp' folder (for the javascript-based Vue application running in Vite) pictured to the right, you will find the following folders with descriptions of what they do. Top-Level Files are described in section 2. The main source code for the Vue application is covered in section 3 - The Src Folder.

---

#### /.vscode
This folder contains files for running the application, particulairly with VsCode. File 'extensions.json' suggests extensions that are useful or necessary for running this application. File 'launch.json' is important for configuring the browser that is launched by both Visual Studio Code and Visual Studio 2022 or 2026. File 'settings.json' is where user and workspace configurations are stored, allowing you to customize the editor.

---

#### /dist
The dist folder (short for "distribution") in a Vue / Vite application contains the production-ready, optimized, and minified static files generated by the build process. These files are what you actually deploy to a web server. 

---

#### /node_modules
The node_modules folder in a Vue / Vite application serves two primary functions: it stores all project dependencies installed via npm (Node Package Manager), and it contains a hidden .vite subfolder used by Vite for caching and pre-bundling dependencies. See the 'package.json' entry below for how this folder is populated.

---

#### /obj
Holds build output and intermediate files for .NET projects. This folder is auto-generated and not meant for manual editing. It should not be checked into source control

---

#### /public
Contains static assets (images, favicon, etc.) that are served directly by the web server. Files here are not processed by the build tool.

### Top Level Files
---

#### The files in the root of the VueApp are all important environment and configuration files. 

---

#### .env, .env.production, .env.qa
Environment variable files for different deployment environments. They store configuration values such as API endpoints, feature flags, and secrets.

#### .eslintrc.cjs
Configuration file for ESLint, which is used to enforce code quality and style rules.

#### .gitignore
Specifies files and directories that should be ignored by Git version control, such as build outputs and local configuration files.

#### aspnetcore-https.js
Script for managing ASP.NET Core HTTPS development certificates, typically used when integrating with a .NET backend.

#### index.html
The main HTML entry point for the Vue application. It loads the JavaScript bundle and mounts the app.

#### jsconfig.json
For VSCode IntelliSense (so auto-imports, jump-to-definition, etc. work), you also need this file at the root of your project.

#### nuget.config
Configuration file for NuGet, the .NET package manager. It specifies package sources and settings for .NET dependencies.

#### package.json / package-lock.json
**package.json** is the configuration file for npm. It contains essential metadata about the project, including the project name, version, scripts for building and running the application, and a list of dependencies required for the project to function properly. **package-lock.json** locks each dependency to an exact resolved version so installs are reproducible.

#### postcss.config.js
Configuration for PostCSS, a tool for transforming CSS with plugins (e.g., autoprefixer, Tailwind CSS).

#### README.md
This file contains documentation for the project. It typically includes an overview of the project, installation instructions, usage examples, and any other relevant information that helps users understand and work with the project.

#### tailwind.config.js
Configuration for Tailwind CSS, specifying custom themes, plugins, and design tokens.

#### vite.config.mjs
Configuration file for Vite, the frontend build tool. It defines plugins, server options, and build settings. This is also where the `unplugin-vue-router` and auto-import/auto-component plugins are registered, which is what generates everything under **/src/autogenerated** (see below).

#### vueapp.esproj
Project file for the Vue frontend, used by Visual Studio for project management and build integration.

### Example Component

#### src/components/boxes/InfoBox.vue
This Vue component file utilizes the **`<script setup>`** syntax for the Composition API. It imports the **useAppStore** function to access the application store and employs **storeToRefs** to create reactive references to the **infoLevel** property from the store. The template conditionally renders a **`<div>`** element containing a slot for content, which is displayed only if **infoLevel** is greater than 1. This component is specifically designed to wrap around content that should only be visible when the **infoLevel** is set to either Info (2) or Help (3).

### The Src Folder
The **/src** directory contains the main source code for the Vue application, including components, pages, stores, utilities, and styles. Below is an alphabetical breakdown of its top-level folders and files.

#### /autogenerated
Holds files that are entirely **machine-generated** by Vite plugins on every dev-server start or build — never edit them by hand and don't bother resolving merge conflicts in them, just regenerate. `.eslintrc-auto-import.json` tells ESLint about auto-imported globals so it doesn't flag them as undefined. `auto-imports.d.ts` provides TypeScript/IntelliSense types for auto-imported Vue, Pinia, and composable APIs (from `unplugin-auto-import`). `components.d.ts` provides types for globally auto-registered components (from `unplugin-vue-components`). `typed-router.d.ts` provides the typed route names/params generated from the **/src/pages** folder structure (from `unplugin-vue-router`).

#### /components
Small, reusable, presentational Vue components with no route of their own — the building blocks used by pages and other components. Code placed here is expected to be reusable and is likely to be used in multiple places across the app, so it should stay generic and avoid depending on any one specific page's state. Organized into subfolders by category:

- **boxes** — bordered content containers like `InfoBox.vue`, `DetailBox.vue`
- **buttons** — `PrimaryButton.vue`, `BooleanButton.vue`, `CircleButton.vue`, etc.
- **calendar** — calendar grid/day/event pieces
- **controls** — interactive UI controls such as `ModalControl.vue`, `AccordionControl.vue`, `SideDrawerControl.vue`, `WizardControl.vue`
- **files-folders** — file/folder browsing and editing widgets
- **inputs** — form input wrappers like `TextInput.vue`, `SelectInput.vue`, `DateInput.vue`
- **layout** — structural chrome such as `NavBar.vue`, `SubNavBar.vue`, `AppSidebar.vue`
- **misc** — grab-bag utilities like `ContextMenu.vue`, `ConwaysLifeGame.vue`, `CodeBlock.vue`
- **pager** — list paging controls
- **realtime** — SignalR-backed chat UI

#### /composables
Vue Composition API functions (the `useXxx.js` convention) that encapsulate reusable, stateful logic shared across components — e.g. `UseAlertControl.js`, `UseSignalR.js`, `UsePagedList.js`, `UseKeyboardListeners.js`. The Composition API makes this possible: instead of a component's logic being locked into rigid `data`/`methods`/`computed` options, related reactive state, computed values, and functions can be grouped together by *concern* and broken out into their own file. Any component can then pull in just the pieces of functionality it needs, so the same piece of logic (an alert system, a paged list, a keyboard listener) doesn't have to be rewritten or copy-pasted into every component that needs it. These composables are auto-imported project-wide, so components can call them without an explicit `import`.

#### /datalists
Static, hard-coded data arrays and lookup lists used to seed dropdowns, examples, and demos — e.g. `usStatesList.js`, `roleList.js`, `fruitsList.js`, `sampleCalendarEvents.js`, plus a **/json** subfolder of raw sample JSON payloads (`30Posts.json`, `simpleExample.json`).

#### /helpers
Plain JavaScript utility modules and directives with no Vue reactivity of their own, e.g. `validators.js`, `global.js`, `fileFolderHelpers.js`, `toolTipDirective.js`/`toolTipPlugin.js`, and the Conway's Game of Life helpers `lifeAlgorithms.js`/`lifePatterns.js`.

#### /layouts
Top-level `<router-view>` wrapper components (`LayoutMain.vue`, `LayoutAuth.vue`, `LayoutNoNav.vue`) that define the outer page chrome — nav bars, sidebars, footers — for groups of routes. A page picks its layout via route metadata, and the matched **pageviews** component is rendered inside it.

#### /markdown
Documentation written in Markdown and rendered inside the app itself (via `MarkdownEditor.vue`/`markdown.css`), including this file, [FilesFoldersHierarchy.md](FilesFoldersHierarchy.md), and `src.md`.

#### /models
Plain JS classes/factories describing the shape of domain data passed between the API and the UI, e.g. `AccountModel.js`, `UserModel.js`, `EventModel.js`, `MessageModel.js`, `PagerModel.js`.

#### /pages
**Used to build the structure of the site.** This folder is consumed directly by `unplugin-vue-router` (see **/router** below) — every `.vue` file and folder here is scanned and converted into a route, so you never hand-write route definitions. Conventions used throughout this folder:
- A file `foo.vue` next to a folder `foo/` becomes the layout/parent route for the routes generated from that folder (e.g. `accounts.vue` + `accounts/`).
- `index.vue` inside a folder becomes that folder's default child route (e.g. `accounts/main/index.vue` → `/accounts/main`).
- `[search].vue` / `[search]/` denote a required dynamic route param (`/examples/:search`).
- `[[fullscreen]].vue` denotes an **optional** dynamic route param.
- `[...path].vue` is the catch-all route used for the 404/not-found page.
Files in **/pages** are meant to stay thin and only define routing — try to avoid putting real markup or logic directly in them, and instead put that logical content into a named component in **/pageviews**, which the page file then just imports and renders. This keeps routing concerns separate from page content.

#### /pageviews
The actual page content components rendered by the routes defined in **/pages** — organized into the same feature subfolders (**accounts**, **admin**, **auth**, **content**, **examples**, **home**, **layout**). Unlike **/components**, code here is for a specific pagelet and typically only appears in the one place it was built for, rather than being written for reuse. This is where page-level composition happens: fetching data, arranging **/components**, and wiring up **/stores**. The **examples** subfolder additionally contains **interview** and **views** folders holding the individual demo pages shown in the Examples section of the site.

#### /router
Contains `router.js`, which configures `vue-router` for the app. Route generation itself is handled by the `unplugin-vue-router` Vite plugin: it watches **/src/pages** and auto-generates the route table (typed in `/src/autogenerated/typed-router.d.ts`) from the file/folder conventions described above, imported here via `vue-router/auto`. `router.js` then layers app-specific behavior on top of that generated table — `extendRoutes()` injects redirects (e.g. `/home` → `/home/intro`) and a root `/` → `/home/intro` fallback, `beforeEach()` enforces authentication on non-public routes via `AuthStore`, and `afterEach()` resets the document title.

#### /stores
Pinia store modules holding global, reactive application state — e.g. `AppStore.js`, `AuthStore.js`, `AccountsStore.js`, `ChatStore.js`, `ToastStore.js`, `UploadStore.js`. Components and composables read/mutate this state instead of passing it through props.

#### /styles
Global and shared style files: `tailwind.css` (Tailwind entry point), `markdown.css` (styling for rendered Markdown), and `toaster.css` (notification/toast styling).

#### /tests
Unit tests (`*.test.js`) for composables and stores, e.g. `ApiErrorHandler.test.js`, `ToastStore.test.js`.

#### App.vue
The root Vue component. Renders the `<router-view>` that swaps in the active **layout** for the current route.

#### createVueApp.js
Entry point that creates and configures the Vue app instance — installs Pinia, the router, and any global plugins/directives — before mounting it to the DOM.
